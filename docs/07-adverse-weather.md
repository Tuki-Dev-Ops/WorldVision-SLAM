# 07. 악천후(눈·비·야간) 실데이터 — 설계와 작업량 산정

> 이 문서는 **결과가 아니다.** 아직 아무것도 내려받지 않았고 아무것도 돌리지 않았다.
> 여기 적힌 것은 (1) 파이프라인이 실제로 요구하는 입력 계약을 코드에서 실측한 것,
> (2) 후보 데이터셋 넷이 그 계약의 어디에서 어긋나는지, (3) 그 격차를 메우는 변환기의
> 설계와 작업량, (4) **이 실험을 무효로 만들 수 있는 것들** 이다.
> 06-results.md 의 문체를 따른다 — 실패와 한계를 먼저 적는다.

## 0. 한 문단 요약

`tools/kitti_convert.cpp` 가 KITTI 를 먹을 수 있는 이유는 KITTI 가 **정렬된 스테레오 쌍**과
**프레임마다 하나씩 대응하는 정답 포즈**를 둘 다 주기 때문이다. 후보 넷 중 이 두 가지를
동시에 주는 것은 **하나도 없다.** 각각은 둘 중 하나를 빠뜨리고, 빠뜨린 쪽을 우리가
만들어 넣는 순간 그것은 더 이상 정답이 아니라 추정값이 되며, 그 추정값으로 채점한
ATE 는 알고리즘의 오차가 아니라 **우리가 만든 정답의 오차와 알고리즘 오차의 합**이 된다.
이 문서의 결론은 "어느 데이터셋이 좋은가" 가 아니라 **"어느 데이터셋이 이 오염을 가장
적게 들여오는가"** 이다.

넷 안에서의 답은 **CADC** 다 — 유일하게 정답이 진짜 정답(GNSS+INS+후처리 RTK)이고,
부족한 것이 정렬 하나뿐인데 정렬은 추정이 아니라 계산이기 때문이다.
**넷 밖에서의 답은 `4Seasons`(TUM) 다** (§3.4). 스테레오 30 cm 베이스라인과 cm 급 융합
포즈를 눈·비·야간에서 동시에 주는 유일한 후보이고, 그 유일한 결격이라던 "흑백" 은
**이 파이프라인이 어차피 영상을 그레이로 읽기 때문에 결격이 아니다.**

## 1. 입력 계약 — 코드에서 실측한 것

추측이 아니라 파일을 읽고 적었다. 인용한 줄 번호는 현재 HEAD 기준이다.

### 1.1 소비자가 실제로 여는 파일

`tools/tum_odometry.cpp` (그리고 `tum_baseline` / `tum_fusion` / `tum_loopclose` /
`bench_run.py`) 는 **시퀀스 루트 하나**를 인자로 받고 그 안에서 다음을 연다.

| 경로 | 필수 | 내용 |
|---|---|---|
| `<root>/rgb.txt` | **필수** | `# ` 주석 허용, `<timestamp[s]> <상대경로>` 공백 구분 |
| `<root>/depth.txt` | **필수** | 같은 형식 |
| `<root>/rgb/*.png` | 필수 | `cv::IMREAD_GRAYSCALE` 로 읽는다 — 컬러여도 그레이로 죽는다 |
| `<root>/depth/*.png` | 필수 | `cv::IMREAD_UNCHANGED`, 16-bit 단채널 가정 |
| `<root>/groundtruth.txt` | 채점에만 | `<t> tx ty tz qx qy qz qw`, TUM 규약 |
| `<root>/calib.txt` | 선택(사실상 필수) | 아래 §1.3 |

`rgb.txt` 에 적혔지만 디스크에 없는 파일은 **조용히 건너뛴다** (`tum_odometry.cpp:444`,
`if (!fileExists(rgb_file)) continue;`). 이것이 §25.22 에서 16 개 TUM 시퀀스 중 13 개가
시퀀스의 일부만 채점하고 있었던 원인이고, `python/tools/check_datasets.py` 가 존재하는
이유다. **새 변환기는 인덱스와 디스크가 어긋난 배치를 절대 내보내면 안 된다.**

### 1.2 RGB↔깊이↔정답 의 시간 결합 — 허용 오차 0.02 s (하드코딩)

```cpp
// tools/tum_odometry.cpp:446
const int di = nearest(depth_rows, rr.stamp, 0.02);
if (di < 0) continue;
```

그리고 채점 쪽도 같다 — `python/wme/eval/trajectory.py:38`, `associate(..., max_difference: float = 0.02)`,
`python/wme/eval/tum.py:127` 도 동일. 즉 **20 ms**.

이것이 악천후 데이터셋에 그대로 꽂히는 제약이다. 차량 데이터셋의 GNSS/INS 정답은 흔히
10–100 Hz 이지만 카메라 트리거와 위상이 맞지 않고, 어떤 데이터셋은 정답이 1 Hz 다.
**1 Hz 정답을 10 Hz 프레임에 붙이면 10 프레임 중 9 개가 조용히 버려지고**, 남은 1 개로
계산된 ATE 는 여전히 표에 숫자로 실린다. 변환기는 정답을 **프레임 시각으로 보간해서**
써야 한다 — 위치는 선형, 회전은 SLERP. 보간 자체가 오차를 만들지만, 20 ms 창을 넘겨
프레임을 잃는 것보다 낫고 **무엇보다 그 오차는 계산할 수 있다**.

### 1.3 `calib.txt` — 필수 키와 기본값의 함정

`tools/dataset_calib.hpp` 가 파싱한다. 형식은 `키: 값` 한 줄 하나, `#` 주석.

```
fx: 707.0912      # 필수
fy: 707.0912      # 필수
cx: 601.8873      # 필수
cy: 183.1104      # 필수
width: 1226       # 필수
height: 370       # 필수
depth_scale: 256  # 필수 (필수 6개 중 하나로 셈)
depth_min: 3.2    # 선택 — 하지만 없으면 TUM 기본 0.1 m 가 남는다
depth_max: 80     # 선택 — 하지만 없으면 TUM 기본 8.0 m 가 남는다
dist: 0 0 0 0 0   # k1 k2 p1 p2 k3
```

`loadDatasetCalib` 는 `fx/fy/cx/cy/width/height/depth_scale/dist` 중 **6 개 미만**이
읽히면 실패시킨다(`dataset_calib.hpp:126`). 파일이 아예 없으면 실패가 아니라 **경로
문자열에 `freiburg2`/`freiburg3` 가 들어있는지로 TUM 내부파라미터를 고른다**
(`defaultCalibForPath`). 헤더 주석이 직접 경고하는 함정이다:

> KITTI 시퀀스 경로에는 freiburg 가 없으므로 fr1 값(fx=517, 640×480)이 1241×376 영상에
> 적용되고, 결과는 실패가 아니라 그럴듯한 오차로 나온다.

**악천후 배치는 이 함정을 그대로 밟는다.** `data/cadc_0001` 같은 경로에는 freiburg 가
없으므로 `calib.txt` 를 빠뜨리면 fx=517.3 / 640×480 / depth_scale=5000 / 깊이범위
[0.1, 8.0] m 가 조용히 적용된다. 차량 장면에서 상한 8 m 는 특징점의 거의 전부를 버리고,
그 상태로도 ATE 는 계산되어 표에 실린다.

`depth_min`/`depth_max` 를 반드시 써야 하는 이유는 헤더 주석에 실측으로 남아 있다 —
KITTI 유효 깊이 중앙값 13.9 m, 최대 47.9 m 이므로 TUM 기본 상한 8.0 m 를 쓰면
프레임당 3D 대응이 164 → 35 개로 떨어지고 400 프레임 중 371 프레임이 추적에 실패했다.

### 1.4 왜곡 — 보정은 소비자가 한다, 단 새 K 를 원본 K 로 고정한 채로

```cpp
// tools/tum_odometry.cpp:314
cv::initUndistortRectifyMap(Kcv, dist, cv::Mat(), Kcv, cv::Size(K.width, K.height), CV_16SC2, map1, map2);
...
cv::remap(gray_raw, gray, map1, map2, cv::INTER_LINEAR);
cv::remap(depth_raw, depth, map1, map2, cv::INTER_NEAREST);   // 깊이는 반드시 최근접
```

`newCameraMatrix` 를 원본 `K` 로 **고정**한다. 즉 이 파이프라인은 "왜곡만 편다, 시야각과
내부파라미터는 그대로" 를 전제한다. 따라서 변환기가 취할 수 있는 길은 둘 중 하나다.

- **(A) 변환기가 이미 편 영상을 내보내고 `dist: 0 0 0 0 0` 을 쓴다.** `kitti_convert` 가
  하는 방식이고, 스테레오 정렬을 하려면 어차피 여기로 와야 한다.
- **(B) 원본을 그대로 두고 `dist:` 에 계수를 적는다.** 단안 배치에서만 가능하다.
  스테레오 깊이를 만들려면 정렬이 필요한데 `dist` 는 정렬(회전)을 표현하지 못한다.

**깊이 리샘플에 최근접을 쓰는 이유**는 코드 주석에 있다 — 선형 보간을 쓰면 무효값 0 과
실제 깊이가 섞여 허공에 점이 생긴다. 변환기가 자체 리샘플을 할 때도 같은 규칙이다.

### 1.5 깊이 인코딩 관례

- 16-bit PNG 단채널. **0 = 무효.** TUM 의 결측 표기와 같게 맞춘 것이라 하류가 이미 다룰 줄 안다.
- 미터 = PNG 값 / `depth_scale`.
- `kitti_convert.cpp:176` 은 `kDepthScale = 256.0` 을 **상수로 박아 두고** 근거를 적는다:
  80 m × 256 = 20480 < 65535. TUM 은 5000 (실내 ~13 m 상한).
  악천후 차량 데이터도 80 m 급이므로 **256 을 그대로 쓰는 것이 맞다.**
- 65535 를 넘는 값은 0(무효)으로 떨어뜨린다 (`kitti_convert.cpp:232`).

### 1.6 스테레오 — `StereoDepth` 가 요구하는 것

`include/wme/perception/StereoDepth.hpp:63-65` 가 계약을 한 줄로 적어 둔다:

> `left`/`right` 는 같은 크기의 CV_8U(그레이) 또는 CV_8UC3. **정렬(rectified)되어 있다고
> 가정한다** — KITTI/EuRoC 는 이미 그렇다.

즉 `StereoDepth` 는 정렬을 **하지 않는다.** 확인도 하지 않는다. 정렬되지 않은 쌍을 넣으면
SGBM 은 같은 행에서만 대응을 찾으므로 시차가 깊이가 아니라 잡음이 되고, 그것은 실패로
보고되지 않는다.

필요한 값은 `StereoDepthConfig` 의 두 개다.

| 필드 | KITTI 에서 어떻게 얻는가 | 악천후 데이터셋에서 무엇이 필요한가 |
|---|---|---|
| `focal_px` | `calib.txt` 의 `P0[0]` | 정렬 후 좌영상의 fx |
| `baseline_m` | `B = −P1[0,3] / fx` | 정렬 후 좌우 광학중심 거리 [m] |

`P1 = K[I|t]`, `t_x = −f·B` 라는 **KITTI 의 투영행렬 규약**에 의존한다
(`kitti_convert.cpp:53-73`). 실측 확인: `data/kitti/dataset/sequences/04/calib.txt` 의
`P1[0,3] = −379.8145`, `fx = 707.0912` → `B = 0.5372 m`.
다른 데이터셋은 이 규약을 쓰지 않는다 — 대개 `T_cam0_cam1` 4×4 행렬이나 쿼터니언+평행이동을
주므로, 변환기가 `stereoRectify` 를 돌려 **정렬 후** 값을 다시 계산해야 한다.

### 1.7 시차 범위는 유도된 값이다 — 대충 두면 조용히 틀린다

이것이 §25.19 의 핵심이고, 새 데이터셋마다 다시 계산해야 하는 유일한 상수다.

```cpp
// StereoDepth.cpp:24
int StereoDepth::requiredDisparities(double focal_px, double baseline_m, double min_depth_m) {
    const double d = focal_px * baseline_m / min_depth_m;
    return std::max(16, static_cast<int>(std::ceil((d + 1.0) / 16.0)) * 16);
}
```

`kitti_convert` 는 `--min-depth` 기본값 4.0 m (KITTI 도로 장면의 최근접 거리, 실측 근거
있는 값) 로 이것을 부른다. seq 04 에서 `707.09 × 0.5372 / 4.0 = 94.97` → 96,
seq 00 에서 `718.86 × 0.537 / 4.0 = 96.5` → 112.

**모자라면 실패하지 않는다.** `StereoDepth.cpp:84-89` 의 주석이 실측을 적어 둔다 — TUM(1~5 m)에
KITTI 베이스라인 0.54 m 를 쓰면 참 시차 140 px 인데 범위가 128 px 이라 중앙 깊이 스케일이
**2.34 배**로 나왔다. 그래서 `StereoDepthResult` 는 `clipped_ratio` 를 반드시 같이 내고,
`kitti_convert` 는 2 % 를 넘으면 경고한다.

악천후 데이터셋은 베이스라인이 KITTI(0.54 m)와 다르다. 베이스라인이 커지면 같은 최근접
거리에 더 넓은 시차 범위가 필요하고, SGBM 비용은 시차 범위에 선형이다. **이 값은 데이터셋마다
새로 유도해야 하고, 유도하지 않으면 결과가 조용히 틀린다.**

### 1.8 정답 포즈 형식

`kitti_convert.cpp:249-256` 이 KITTI 의 3×4 행 우선 행렬 12 개를 읽어 `toQuat` 로 쿼터니언을
만들고 TUM 형식으로 쓴다. **좌표계는 그대로 통과시킨다** — KITTI 포즈는 첫 프레임의
좌 카메라 좌표계 기준이고, ATE 는 Umeyama 정렬 후 RMSE 이므로 (`bench_report.py:95`)
전역 강체 변환은 상쇄된다. 다만 **스케일은 상쇄되지 않는다** (기본 `align=True, with_scale=False`).

따라서 변환기가 정답을 어느 좌표계로 내보내든 상관없지만, **미터 단위여야 하고 카메라와
정답이 같은 강체에 붙어 있어야 한다.** GNSS/INS 정답은 대개 IMU/안테나 좌표계이므로
`T_cam_imu` 외부파라미터를 곱해 카메라로 옮겨야 한다 — 이 곱을 빠뜨리면 안테나-카메라
레버암(차량에서 보통 0.5–1.5 m)이 통째로 궤적 오차로 들어가고, ATE 수십 cm 대의 실험에서
그것은 신호보다 크다.

### 1.9 정리 — 변환기가 반드시 만들어 내야 하는 것

```
<out>/rgb/000000.png       8-bit, 정렬된 좌영상 (그레이로 읽힌다)
<out>/depth/000000.png     16-bit 단채널, 0=무효, 미터 = 값/depth_scale
<out>/rgb.txt              # timestamp filename   (초 단위 double)
<out>/depth.txt            rgb.txt 와 같은 시각 (20 ms 안)
<out>/groundtruth.txt      # timestamp tx ty tz qx qy qz qw, 프레임 시각으로 보간, 카메라 좌표계
<out>/calib.txt            fx fy cx cy width height depth_scale depth_min depth_max dist
```

그리고 **`rgb.txt` 의 모든 줄에 대응하는 파일이 실제로 존재해야 한다.**

### 1.10 베이스라인이 정하는 것 — 깊이 예산은 데이터셋 선택보다 먼저 온다

§1.7 의 두 공식으로 각 후보 리그의 **쓸 수 있는 깊이 상한**이 데이터를 받기 전에 계산된다.
`StereoDepth::minValidDisparity` 는 기본 `disparity_noise_px = 0.5`, `max_depth_sigma_m = 3.0`
(`kitti_convert` 가 설정하는 값) 에서 `d_min = √(f·B·σ_d/σ_Z)` 를 주고, 그 위의 깊이는
버려진다. 즉 **사용 가능 최대 깊이 = f·B / d_min = √(f·B·σ_Z/σ_d)**.

| 리그 | f·B [px·m] | 최소 유효 시차 | **쓸 수 있는 최대 깊이** | 시차범위(4 m) | σ_Z @ 40 m |
|---|---|---|---|---|---|
| KITTI seq 00 (f=718.9, B=0.537) | 386.0 | 8.02 px | **48.1 m** | 112 | 2.07 m |
| KITTI seq 04 (f=707.1, B=0.537) | 379.8 | 7.96 px | **47.7 m** | 96 | 2.11 m |
| SID / ZED (f≈640–700, B=0.120) | 77–84 | 3.6–3.7 px | **21.5–22.4 m** | 32 | 9.5–10.4 m |
| CADC 가정 B=0.20 (f≈510) | 102.0 | 4.12 px | **24.7 m** | 32 | 7.84 m |
| CADC 가정 B=0.50 (f≈510) | 255.0 | 6.52 px | **39.1 m** | 80 | 3.14 m |

> **이 표의 첫 두 줄은 검산이다.** `dataset_calib.hpp` 의 주석은 KITTI 유효 깊이의 실측
> **최대가 47.9 m** 라고 적어 두었다. 위 공식이 데이터 없이 48.1 / 47.7 m 를 준다. 즉 이
> 예산 모델은 이 저장소의 실측과 일치하며, 아래 미측정 리그에 대한 예측도 같은 신뢰도로
> 읽어도 된다. CADC 행의 f 와 B 는 **가정값**이다 (§2.1 — 베이스라인이 공개 문서에 없다).

읽어야 할 결론은 하나다. **짧은 베이스라인은 "조금 나쁜" 것이 아니라 장면의 대부분을
잘라낸다.** SID 의 ZED(120 mm)는 KITTI 대비 f·B 가 4.6–5.0 배 작아 쓸 수 있는 깊이가
48 m → 22 m 로 내려앉는다. 그리고 이것은 `dataset_calib.hpp` 가 경고하는 바로 그 상황의
축소판이다 — 상한이 장면을 잘라내면 프레임당 3D 대응이 무너지고, 추적 실패가 늘고,
**그런데도 ATE 는 계산되어 표에 실린다.** 40 m 지점 σ_Z 가 9.5 m 라는 것은 그 거리의
깊이가 정보가 아니라 잡음이라는 뜻이다.

역으로 짧은 베이스라인의 유일한 이득은 시차범위가 112 → 32 으로 줄어 SGBM 이 3 배
싸진다는 것뿐이고, 그것은 우리가 사려는 물건이 아니다.

> 쌍이 아니다" 라는 요약을 한 번 만났다. 위 표의 `trinocular` 항목은 그 요약이 아니라

### 3.2 순위와 근거

**1위 — CADC.** 유일하게 **정답이 진짜 정답이다.** GNSS + INS + 베이스국 후처리 RTK 는
우리가 만드는 것이 아니라 독립 센서가 잰 것이고, 그래서 §7 의 첫 항목(정답을 우리가
만들면 실험이 아니다)을 유일하게 피해 간다. 부족한 것은 **정렬 하나뿐이고, 정렬은
`cv::stereoRectify` 로 계산되는 결정적 연산이다** — 추정이 아니다. 논문이 전방 3 대를
trinocular 로 배치하고 *"allowing for convenient rectification if needed"* 라고 명시했고,
`extrinsics.yaml` 에 카메라 간 4×4 변환이 들어 있다. 여기에 LiDAR 가 있어 §26 이 남긴
"스테레오 깊이가 KITTI 의 Velodyne 과 대조된 적이 없다" 항목까지 부수적으로 닫힌다.

비용은 정직하게 크다 — 연속 궤적을 쓰려면 `raw` 472.7 GB 이고, 라이선스가 비상업이며,
**베이스라인 수치를 아직 모른다.** 그 마지막 항목이 1 위 자리를 조건부로 만든다.

**2위 — SID.** 파이프라인 입력으로서는 넷 중 가장 매끄럽다. 정렬된 PNG 를 그대로 넣으면
되고, 눈 80,317 쌍 · 야간 44,020 쌍은 넷 중 조건 커버리지가 가장 좋으며, CC BY 4.0 이라
라이선스 마찰도 없다. **그런데 정답이 없다.** 그리고 없는 정답을 우리가 만들면 §7 의
첫 항목에 정면으로 걸린다.

따라서 SID 의 올바른 쓰임은 ATE 실험이 아니다. **정답 없이도 셀 수 있는 것**만 세는 것이다 —
추적 유지율, 프레임당 유효 3D 대응 수, `valid_ratio`, `EnvironmentAnalyzer` 의
`rain_streak`/`snow_particle` 이 실제로 발화하는지(§6.2). 이것들은 전부 자기보고 지표라
정답을 요구하지 않고, **§25 의 실패 검출기 계열이 악천후에서 무엇을 하는지**를 답한다.
그것만으로도 이 저장소에 없는 결과다. 다만 그것을 "ATE 결과" 라고 부르면 안 된다.

**3위 — WADS.** 영상이 배포되지 않는다. 파이프라인에 넣을 것이 없다. 순위에 넣은 이유는
"어렵다" 가 아니라 **"불가능하다"** 를 기록하기 위해서다. 원 수집 데이터 26–36 TB 에는
카메라와 RTK GNSS 가 있었으므로 저자에게 요청하는 경로가 이론상 있지만, 그것은 데이터셋
채택이 아니라 협업 요청이고 이 산정의 범위 밖이다.

**4위 — IDD-AW.** 스테레오도, 포즈도, **시간 연속성도** 없다. 앞의 둘은 하드웨어의 문제고
마지막은 **설계 의도**다 — 3 초 임계로 반복 프레임을 걸러낸 것이 이 데이터셋의 기여다.
SLAM 은 프레임 간 연속성 위에 서 있으므로 이것은 격차가 아니라 **범주 오류**다.
좋은 데이터셋이고, 우리 목적이 아닐 뿐이다.

### 3.3 없는 것을 무엇으로 대체할 것인가 — 그리고 대체의 대가

| 없는 것 | 대체 수단 | 대가 |
|---|---|---|
| **정렬** (CADC) | `cv::stereoRectify` + `initUndistortRectifyMap` | **작다.** 결정적 연산이고, 정렬 품질은 세로 시차로 **측정 가능**하다. 유효 시야가 조금 잘리는 것이 전부 |
| **깊이** (스테레오가 없을 때) | LiDAR 를 영상에 투영해 희소 깊이 생성 | 중간. 하지만 **파이프라인이 조밀 깊이를 전제한다** — `depth` 는 `cv::Mat` 조밀 맵이고 무효는 0 이다. 희소 LiDAR 는 `valid_ratio` 를 수 % 로 떨어뜨려 ECDA 의 점 수가 무너진다. 보간하면 그 순간 깊이는 다시 추정값이 된다 |
| **포즈** (SID) | SfM / LiDAR-SLAM 으로 유사정답 생성 | **치명적.** §7 첫 항목. 정답이 추정값이 되고, 악천후에서 그 추정값이 가장 나빠지므로 **정답의 오차가 측정하려는 신호와 상관된다.** ATE 를 발표할 수 없다 |
| **시간 연속성** (IDD-AW) | 없음 | 대체 불가 |
| **영상** (WADS) | 없음 | 대체 불가 |

이 표의 요점은 첫 행과 셋째 행의 대비다. **정렬을 만드는 것은 계산이고, 포즈를 만드는
것은 실험을 바꾸는 것이다.** 그래서 CADC 가 1 위다 — 우리가 만들어야 하는 것이
계산이지 정답이 아니기 때문이다.

깊이 예산(§1.10 과 같은 계산)도 나쁘지 않다.

**그리고 RobotCar 에는 이 문서가 발견한 것 중 가장 중요한 함정이 하나 있다.**
눈 traversal 은 `2015-02-03-08-45-10` **단 하나**이고, RTK 정답 릴리스는 벤치마크용으로
일부 traversal 을 보류(withheld)하는데 **그 목록에 유일한 눈 traversal 이 들어 있다.**
즉 RobotCar 로는 **"눈 + 신뢰할 수 있는 정답"** 조합이 사실상 성립하지 않는다.
비와 야간은 가능하다 — 이것이 `03-roadmap.md` 의 항목이 정확히 "night + rain" 이라고
적혀 있는 이유일 수 있고, 그렇다면 그 TODO 는 눈까지 덮지 못한다.

**따라서 수정된 권고는 이렇다.**

1. **4Seasons** — 두 요구를 모두 만족하는 유일한 후보. 넷 중 어느 것도 하지 못한 일이다.
   흑백은 이 파이프라인에서 문제가 아니다. **다만 이 저장소는 아직 4Seasons 를 한 번도
   조사한 적이 없고, 위 표의 항목 중 fx·정확한 배포 형식·용량·접근 조건은 미확인이다.**
2. **CADC** — 넷 중 1 위. 정답이 진짜 정답이고 부족한 것이 정렬 하나뿐. 눈에 특화.
3. **Oxford RobotCar** — 비·야간 한정. 로드맵이 이미 지목한 것이므로 §26 의 항목을
   직접 닫는다. traversal 당 스테레오 약 48 GB + INS 20 MB + RTK 91 MB 로,
   **필요한 것만 받는 것이 가능한 유일한 후보다.**
4. **SID** — 정답 없이 셀 수 있는 것만 (§3.2).

라이선스는 4Seasons / RobotCar / CADC 가 모두 **비상업**(CC BY-NC-SA 4.0 또는 CC BY-NC 4.0)
이라는 점이 공통된다. 상업 이용이 요건이면 후보가 SID(CC BY 4.0) 정도로 줄어들고,
그것은 정답이 없는 쪽이다.

## 4. 변환기 설계

### 4.1 도구를 하나 더 만드는가, `kitti_convert` 를 고치는가

**새 도구를 만든다.** 근거는 `kitti_convert.cpp` 머리말이 이미 적어 둔 것과 같은 논리다 —
KITTI 전용 러너를 새로 쓰지 않고 데이터를 맞춘 이유는 "두 경로가 어긋나는 순간 그 차이가
데이터셋 차이로 오독된다" 였다. 여기서는 반대 방향으로 같은 규칙이 적용된다.
`kitti_convert` 는 **P0/P1 규약과 이미 정렬된 입력**을 전제로 297 줄에 담겨 있고, 여기에
YAML 캘리브 파싱 · `stereoRectify` · GNSS→ENU→카메라 포즈 변환 · SLERP 보간을 끼워 넣으면
**KITTI 경로가 바뀐다.** §25.20–25.22 의 4–0 은 그 경로에서 나온 숫자다. 건드리면 재실행
없이는 그 숫자를 계속 인용할 수 없다.

따라서 `tools/adverse_convert.cpp` (가칭) 를 새로 두고, `StereoDepth` 와 깊이 인코딩
관례만 공유한다. 공유해야 할 것은 코드가 아니라 **출력 형식**이다.

### 4.2 단계별 설계

```
[0] 데이터셋 어댑터        (데이터셋마다 다른 유일한 부분)
      입력: 데이터셋 루트, 시퀀스 ID
      출력: (t, 좌영상경로, 우영상경로) 목록
            K_l, D_l, K_r, D_r, T_cam_l_cam_r
            (t, T_world_body) 목록,  T_body_cam_l
[1] 정렬(rectify)          cv::stereoRectify + initUndistortRectifyMap
      → R1,R2,P1,P2. 여기서 f_rect = P1[0,0], B = -P2[0,3]/f_rect
      → 검증: 정렬 후 세로 시차가 0.5 px 이하인가 (equirect_convert.cpp 의 checkRectified 와 같은 규칙)
[2] 시차 범위 유도         requiredDisparities(f_rect, B, min_depth)
      → clipped_ratio 를 프레임마다 누적, 2 % 초과면 경고 (kitti_convert 와 같은 규칙)
[3] 깊이 생성              StereoDepth::compute → uint16 PNG, depth_scale = 256
[4] 포즈 변환              T_world_cam = T_world_body * T_body_cam_l
      → 프레임 시각으로 보간 (위치 선형, 회전 SLERP)
      → TUM 형식 (t tx ty tz qx qy qz qw)
[5] calib.txt 기록          fx fy cx cy width height depth_scale depth_min depth_max dist(=0)
[6] 자기검사                rgb.txt 의 모든 줄에 파일이 있는가
                           groundtruth.txt 가 모든 프레임 시각을 20 ms 안에 덮는가
                           → 하나라도 어기면 배치를 내보내지 않고 실패한다
```

**[0] 만 데이터셋마다 다르다.** [1]–[6] 은 공통이다. 이 분리가 지켜지면 두 번째 데이터셋의
비용은 첫 번째의 1/3 이하가 된다.

### 4.3 각 단계의 위험

| 단계 | 위험 | 조용한가 | 완화 |
|---|---|---|---|
| [0] | `T_body_cam` 을 빠뜨리거나 방향을 뒤집는다 (`T_a_b` vs `T_b_a`) | **완전히 조용하다.** 레버암 0.5–1.5 m 가 궤적에 상수 오프셋으로 들어가고 ATE 는 그럴듯한 값을 낸다 | 정지 구간에서 궤적이 정지하는지 확인. 두 방향을 모두 돌려 ATE 가 더 낮은 쪽을 채택하지 **않는다** — 그건 정답을 튜닝하는 것이다 |
| [1] | 정렬이 어긋난다 | **조용하다.** SGBM 은 잡음을 시차로 돌려준다 | 정렬 후 세로 시차 상한을 계산해 0.5 px 초과 시 **실패시킨다** |
| [2] | 시차범위 부족 | **조용하다** (§25.19, 스케일 2.34 배) | `clipped_ratio` 누적 + 2 % 경고. 이미 구현되어 있다 |
| [3] | 악천후에서 유효 깊이 비율이 급락 | 반쯤 조용하다 — `valid_ratio` 는 나오지만 아무도 실패시키지 않는다 | 시퀀스별 `valid_ratio` 를 배치 메타에 남기고, 맑은 날 대비 급락을 **결과 해석의 전제**로 보고한다 |
| [4] | GNSS 정답 자체가 악천후에서 나빠진다 (다중경로, 위성 차폐) | **조용하다.** 정답이 흔들려도 정답이라 불린다 | 데이터셋이 주는 공분산/표준편차(예: CADC 의 INSCOV/INSPVAX)를 같이 내보내고, 그 값이 큰 구간을 채점에서 뺄 수 있게 한다 |
| [5] | `calib.txt` 누락 | **조용하다** (§1.3, fr1 기본값이 적용됨) | 변환기가 항상 쓴다. 못 쓰면 실패 |
| [6] | 인덱스와 디스크 불일치 | **조용하다** (§25.22, 13/16 시퀀스가 일부만 채점됨) | 변환기 자체가 검사. `check_datasets.py` 는 사후 안전망이지 1 차 방어가 아니다 |

이 표의 "조용한가" 열이 전부 **예** 인 것이 이 작업의 성격이다. 여섯 단계 중 다섯 개가
틀려도 프로그램은 성공을 보고하고 표에는 숫자가 실린다. 그래서 각 단계마다 **실패시키는
검사**를 같이 만드는 것이 선택이 아니라 작업의 절반이다.

### 4.4 오라클 — 저장소 관례상 생략할 수 없는 것

`equirect_convert` 에는 `python/wme/reference/equirect.py` (numpy 재구현) 와
`python/tools/equirect_validate.py` (차등 검증 + 재투영 오차 + 내부파라미터 회수) 가 붙어
있다. `StereoDepth` 에는 `python/tools/stereo_validate.py` 가 붙어 있고, 그 머리말은 자기
측정이 **자기일관성이지 실제 스테레오 정확도가 아니다** 라고 먼저 밝힌다.

새 변환기도 같은 것을 요구한다. 최소한:

1. **포즈 변환 차등** — `T_world_body · T_body_cam` 합성과 SLERP 보간을 numpy 로 재구현해
   C++ 와 비교. 이것이 §4.3 [0]/[4] 의 조용한 실패를 잡는 유일한 장치다.
2. **정렬 검증** — 정렬 후 좌우 영상에서 대응점을 뽑아 세로 시차 분포를 재고, 상한 0.5 px
   주장을 **데이터로** 확인. 합성이 아니라 실제 쌍으로 해야 의미가 있다.
3. **깊이 스케일 회수** — LiDAR 가 있는 데이터셋(CADC)에서는 SGBM 깊이를 LiDAR 투영과
   비교할 수 있다. **이것은 KITTI 에서도 아직 못 한 것이다** (§26: *"never against KITTI's
   own Velodyne"*). 즉 CADC 를 붙이면 기존 KITTI 결과의 미해결 항목이 부수적으로 닫힌다.

### 4.5 작업량 산정

단위는 사람-일(person-day). 이 저장소의 기존 도구를 기준점으로 삼는다 —
`kitti_convert.cpp` 297 줄, `equirect_convert.cpp` 는 검증 스크립트와 numpy 오라클까지
포함해 훨씬 크다. 아래는 **경험 기반 추정이며 실측이 아니다.**

| 작업 | 사람-일 | 근거 / 위험 |
|---|---|---|

- **정답을 우리가 만들어야 하는 경우의 비용이 빠져 있다.** SID 처럼 포즈가 아예 없는
  데이터셋에 SfM/LiDAR-SLAM 으로 유사정답을 만드는 작업은 위 표 어디에도 없고,
  그것은 며칠이 아니라 별도 프로젝트다. 그리고 §3 이 말하듯 그렇게 만든 정답으로 낸
  숫자는 이 저장소가 발표할 수 있는 종류의 숫자가 아니다.
- **악천후에서 SGBM 이 실제로 어떻게 동작하는지 모른다.** `valid_ratio` 가 KITTI 의
  67–74 % 에서 얼마나 떨어질지 전혀 알 수 없고, 너무 낮으면 변환 자체를 다시 설계해야
  한다. 이것이 산정의 가장 큰 미지수다.
- **ORB-SLAM3 등 published baseline 은 여전히 없다** (§26). 악천후 데이터를 붙여도
  대조군은 자체 구현 ORB + `cv2.Odometry` 두 개 그대로다.

## 6. 합성 열화(§23) 대비 실데이터가 메우는 것과 못 메우는 것

README 는 이미 한 줄로 밝혀 두었다 (README.md:97):

> 열화(안개) 실험은 실제 TUM 프레임에 **실측 깊이**로 산란 방정식을 적용해 만든 것이지,
> 자연 열화 데이터가 아니다

그 문장이 정확히 무엇을 인정하는 것인지, 그리고 실데이터가 그 중 어디까지 메우는지를
나눠 적는다.

### 6.1 §23 이 이미 증명한 것 — 실데이터가 다시 증명할 필요가 없는 것

`tum_degrade.cpp` 의 안개는 근사가 아니다. `I_hazy = I·t + A(1−t)`, `t = exp(−β·d)` 에서
**`d` 가 TUM 의 실측 깊이맵**이므로 투과율은 추정값이 아니라 센서가 보고한 값이다.
그리고 그것이 검증되었다 — 예측 `exp(−βd̄)` 대비 측정 대비비가 네 개 β 전부에서 2 % 안
(§23.1). 어둠은 AGC 재게인 후 평균 불변(142.4)에 σ 1.30 → 3.49, 블러는 진리값 속도로
게이트되어 51 → 201 → 228 → 242 프레임 단조 증가.

**즉 "광학적 열화가 커지면 두 시스템이 어떻게 갈리는가" 는 이미 실데이터 위에서 답이
나와 있다.** WME 는 β ≈ 0.5 까지 앞서다가 무너지고, 자기 자신의 맑은 성능 대비 128 배까지
간다(고전 파이프라인은 6.8 배). §23.3 의 결론 — **둘 다 우아하게 열화되지 않으며 반대
방향으로 실패한다** — 는 실제 악천후 데이터가 있어도 뒤집히지 않을 종류의 관찰이다.

### 6.2 실데이터가 메우는 것

| 합성이 못 하는 것 | 왜 | 실데이터가 주는 것 |
|---|---|---|
| **airlight 가 상수다** | `tum_degrade` 는 A 를 하나의 상수로 둔다 | 실제 안개/눈은 광원과 시선 방향에 따라 airlight 가 변한다. 야간 우천에서는 헤드라이트 역산란이 지배적이다 |
| **파장 의존성이 없다** | 그레이 채널에 균일 적용 | 실제 산란은 파장 의존적이고, 컬러 → 그레이 변환 후에도 대비 구조가 다르다 |
| **입자가 없다** | 안개는 투과율 감쇠일 뿐 화소에 물체가 생기지 않는다 | **비 줄무늬와 눈 입자는 장면 앞의 움직이는 불투명체다.** 감쇠가 아니라 **폐색**이다 |
| **렌즈가 깨끗하다** | 원본 프레임 그대로 | 물방울, 진흙, 성에. `EnvironmentEvidence` 의 `lens_dirt` / `water_drop` 채널이 존재하는 이유 |
| **깊이가 열화되지 않는다** | 의도적 설계 — "둘 다 망가뜨리면 어느 쪽이 원인인지 못 가른다" | 실제 스테레오에서는 **깊이가 같이 무너진다.** 설원의 무텍스처, 눈발의 좌우 비대응, 야간의 SNR 저하가 전부 SGBM 에 직접 들어간다 |
| **노출·화이트밸런스가 고정** | 원본의 것 | 실제 카메라는 AGC/AWB 가 프레임마다 움직이고, 그 자체가 광도 일관성 가정을 깬다 |

이 중 **셋째 줄과 다섯째 줄이 결정적**이다.

**(a) 입자는 감쇠가 아니라 폐색이다.** 이 저장소는 이미 그것을 추정하는 코드를 갖고 있다 —
`src/perception/EnvironmentAnalyzer.cpp:130-202` 의 `estimateParticles` 는 시간 중앙값 대비
**양의 잔차**를 뽑고, 구조텐서 이방성으로 비(줄무늬, 이방성 높음)와 눈(둥근 입자, 이방성
낮음)을 가른다. 그런데 **이 추정기는 지금까지 한 번도 실제 비나 눈을 본 적이 없다.**
`tum_degrade` 의 세 채널(haze/dark/blur) 중 어느 것도 양의 시간 잔차를 만들지 않기
때문이다. §25.17 이 적어 둔 그대로다 — `rain_streak`/`snow_particle` 은 프레임 이력이
필요해서 오라클 커버리지 밖에 남아 있다. **실제 눈·비 데이터는 이 두 추정기를 처음으로
실행시키는 유일한 수단이다.**

**(b) 깊이가 같이 무너지는 것을 §23 은 구조적으로 볼 수 없다.** `tum_degrade` 는 깊이맵을
그대로 복사한다 — 그것이 옳은 설계다(원인 분리). 그런데 그 결과 §23 의 열화 스윕은
**"깊이는 완전한데 영상만 나쁜"** 조건만 잰 것이다. 실제 악천후 스테레오에서는 영상이
나빠지는 바로 그 이유로 깊이도 나빠지고, 두 열화가 상관되어 있다. §25.21 이 KITTI 에서
찾아낸 것 — ECDA 가 스테레오 깊이를 참값으로 믿고 있었고, 깊이 불확실성을 잔차 분산으로
옮기니 2–2 가 4–0 이 되었다 — 는 **깊이가 나쁠 때 무엇이 일어나는지에 대한 실험이고,
악천후는 그 축을 훨씬 세게 미는 조건이다.**

**(c) 그리고 이것이 α_k(E) 의 미결 항목을 정확히 겨눈다.** `03-roadmap.md:47` 이 남긴 문장:

> the fusion weights `α_k(E)` are currently a hand-designed calibration. They must be fit on
> real adverse-condition data before any accuracy claim is publishable.

`python/wme/reference/environment.py:57-58` 의 `(1 − 0.40·rain_streak)`,
`(1 − 0.45·snow_particle)` 두 계수는 **손으로 쓴 숫자다.** 지금까지 이 계수를 데이터로
맞출 방법이 없었다 — 비도 눈도 없었으니까. `visibility` 와 `a0` 에 들어 있는 haze /
darkness / motion_blur 계수는 §23 이 부분적으로 만질 수 있었지만, 비·눈 계수는 손도 못 댔다.

### 6.3 실데이터도 메우지 못하는 것 — 정직하게

- **정답이 악천후에서 같이 나빠진다.** GNSS 는 폭설·폭우에서 다중경로와 위성 차폐로
  나빠지고, INS 는 그 사이를 관성으로 메운다. 즉 **가장 열화가 심한 구간이 정답도 가장
  못 믿을 구간이다.** 이것은 데이터셋을 바꾸어 해결되는 문제가 아니라 이 실험 종류의
  구조적 한계다. 완화책은 하나뿐이다 — 데이터셋이 주는 공분산을 같이 읽고, 그 값이 큰
  구간을 결과에서 **분리해 보고하는 것**.
- **조건별 통제가 사라진다.** §23 의 강점은 β 를 우리가 정한다는 것이었다. 같은 프레임,
  같은 궤적, 같은 깊이에 β 만 다르다. 실데이터에는 그 통제가 없다 — 눈 오는 날의 시퀀스와
  맑은 날의 시퀀스는 **장소도 궤적도 시간도 다르다.** 따라서 실데이터로 얻는 것은
  "열화 강도에 대한 기울기" 가 아니라 "조건별 성능" 이고, 그 둘은 같은 종류의 주장이 아니다.
  **§1 의 헤드라인(이득이 열화와 함께 커진다)은 여전히 §23 의 통제된 스윕이 답해야 한다.**
- **합성 열화를 대체하는 것이 아니라 보완한다.** 위 두 항목 때문에, 실데이터를 붙인 뒤에도
  `tum_degrade` 는 지워지지 않는다. 둘은 서로 다른 질문에 답한다 — 합성은 **기울기**,
  실데이터는 **수준과 실패 양상**.

## 7. 무엇이 이 실험을 무효로 만드는가

06-results.md §26 의 형식을 따라, **먼저 실패할 수 있는 방식**부터 적는다.

- **정답을 우리가 만들면 그 순간 실험이 아니다.** SID 에는 포즈가 없다. SfM 이나
  LiDAR-SLAM 으로 유사정답을 만들 수는 있지만, 그렇게 만든 궤적은 **우리가 재려는 것과
  같은 종류의 추정값**이다. 그것으로 채점한 ATE 는 두 추정기의 차이지 오차가 아니고,
  악천후에서는 유사정답 생성기 자신이 가장 심하게 흔들린다 — 즉 **정답의 오차가 신호와
  상관되어 커진다.** 이것은 편향이 아니라 실험 설계의 무효화다. 이 문서는 그 경로를
  권하지 않는다. 굳이 한다면 **ATE 를 보고하지 말고 실패율·추적 유지율만 보고해야 한다.**
- **레버암/좌표계 오류는 조용하고 크다.** `T_body_cam` 을 빠뜨리면 0.5–1.5 m 의 상수
  오프셋이 궤적에 들어간다. Umeyama 정렬이 상수 오프셋의 일부는 흡수하지만 회전과
  결합된 성분은 흡수하지 못한다. **ATE 수십 cm 를 논하는 실험에서 이것은 신호보다 크다.**
  §25.11 의 교훈 그대로다 — 방향이 뒤집힌 변환은 오류가 아니라 그럴듯한 숫자를 낸다.
- **베이스라인이 짧으면 장면이 잘려 나가고, 그 손실이 알고리즘 탓으로 읽힌다.** §1.10 의
  표대로 SID 의 ZED 는 쓸 수 있는 깊이가 22 m 다. 그 배치에서 나온 나쁜 ATE 는 "WME 가
  눈에 약하다" 가 아니라 "이 리그로는 도로 장면의 깊이를 못 만든다" 일 수 있고,
  **두 설명은 같은 숫자를 낸다.** 최소한의 방어는 같은 데이터셋의 맑은 날 시퀀스를
  대조군으로 함께 돌리는 것이다 — 그러면 리그의 한계는 두 조건 모두에 실린다.
- **`valid_ratio` 가 무너지면 비교가 아니라 다른 실험이 된다.** KITTI 에서 67–74 % 다.
  설원·야간에서 이것이 예컨대 20 % 로 떨어지면, 두 시스템은 같은 알고리즘을 다른 양의
  데이터 위에서 돌린 것이 된다. **`valid_ratio` 는 결과 표의 필수 열이지 진단 정보가 아니다.**
- **서브샘플된 배포본을 연속 시퀀스로 착각하는 것.** CADC `labeled`(92.8 GB) 는 약 3 Hz 다.
  이것으로 오도메트리를 돌리면 프레임 간 이동이 커서 ECDA 가 수렴 반경 밖으로 나가고,
  `tum_odometry` 는 그 실패를 프레임 스킵으로 흡수한다. §25.22 와 정확히 같은 함정 —
  **짧아진 궤적에도 ATE 는 계산되어 표에 실린다.**
- **비상업 라이선스(CADC, CC BY-NC 4.0).** 결과의 용도에 따라 문제가 될 수 있다.
  여기서 판단하지 않고 적어만 둔다.
- **대조군이 여전히 부족하다.** §26 그대로 ORB-SLAM3 / DSO / DROID-SLAM 은 돌아간 적이
  없다. 악천후 데이터를 붙여도 대조군은 자체 구현 ORB 와 `cv2.Odometry` 두 개다.
  **"악천후에서 WME 가 낫다" 는 주장은 그 두 대조군에 대해서만 성립한다.**
- **롤링 셔터(SID).** 이 파이프라인은 한 번도 롤링 셔터 데이터를 다뤄 본 적이 없고,
  §26 이 미해결로 남긴 `fr1_desk` 의 +3.4 % 스케일 편향 후보 중 하나가 바로 롤링 셔터다.
  차량 속도에서 롤링 셔터는 실내 손 움직임보다 훨씬 크게 나타난다.
- **"눈" 이 표본 하나로 줄어드는 것.** RobotCar 의 눈 traversal 은 1 건이고 그것이
  RTK 정답 보류 목록에 있다(§3.4). 시퀀스 하나로 낸 조건별 결과는 조건의 성질이 아니라
  **그 날 그 길의 성질**일 수 있고, §26 이 반복해 적어 둔 "데이터셋의 성질일지 모른다"
  경고가 그대로 적용된다. 눈을 주장하려면 서로 다른 날의 시퀀스가 복수로 필요하다.
- **§1.10 표의 CADC 행은 가정이다.** 베이스라인이 공개 문서에 없다. 그 값이 작으면
  (예 0.2 m) CADC 도 SID 와 같은 깊이 절벽을 만난다. **이 문서 전체에서 가장 값싸게
  해소할 수 있는 미지수이자, 가장 큰 미지수다** — calib 파일 수 MB 면 된다.

## 8. 미확인 목록

이 문서를 쓰면서 확인하지 못한 것들. 추측으로 메우지 않았다.

1. **CADC 스테레오 베이스라인 수치.** 논문·devkit README·XIMEA 자료 어디에도 없다.
   `extrinsics.yaml` 에 있으므로 calib.zip 만 받으면 해소된다. **최우선.**
2. **CADC 카메라 인덱스(00–07)와 방위의 대응.** devkit 이 `cam='0'` 으로 전방 데모를
   만드는 것으로 보아 CAM00 이 전방일 가능성이 높으나 문서화되어 있지 않다.
3. **CADC 공식 호스트의 현재 가용성.** 조사 시점에 `cadcd.uwaterloo.ca:443` ECONNREFUSED.
   공식 URL 이 `http://` 로만 표기되므로 HTTPS 미지원일 가능성이 있으나 확정하지 못했다.
4. **CADC 시퀀스별 정답 궤적의 실측 오차.** 인용한 1 cm / 0.015° 는 Novatel OEM638 의
   **제조사 스펙**이지 이 데이터셋의 검증된 GT 오차가 아니다.
5. **SID `.conf` 캘리브 파일의 내부 키 구성.** StereoLabs 고유 형식이라 파싱기를 새로
   써야 하는데, 무엇을 파싱해야 하는지 아직 모른다.
6. **SID 의 정확한 fx.** §1.10 의 SID 행은 fx 640–700 px 범위 가정이다. 결론(깊이 상한
   22 m 내외)은 그 범위 전체에서 바뀌지 않지만 숫자 자체는 미확정이다.
7. **SID 베이스라인 120 mm.** ZED 1 세대 사양에서 온 강한 추정이지 논문 기재값이 아니다.
8. **WADS 시퀀스별 `README.md` 원문.** 배포 내용물을 확정할 유일한 1 차 문서인데
   호스트가 봇을 차단해 열지 못했다. "영상 없음" 결론은 파일 목록·용량과 제3자 로더
   2 건의 교차검증에 근거한다.
9. **WADS 원 수집 데이터(26–36 TB)의 카메라·GNSS 궤적 공개 가능 여부.** 요청하면 받을
   수 있는지 미확인.
10. **IDD-AW 데이터셋 라이선스.** 명시 문구를 찾지 못했다.
11. **IDD Multimodal 의 정렬 제공 여부와 캘리브 파일 동봉 여부.** 다운로드 없이 확인 불가.
12. **악천후에서 SGBM 의 `valid_ratio`.** 아무도 모른다. 이 문서의 작업량 산정에서
    가장 큰 미지수이며, 데이터를 받기 전에는 알 수 없다.
13. **`raw` CADC 의 실제 프레임 레이트가 전 시퀀스에서 10 Hz 로 유지되는지.** 논문은
    10 Hz 라 하지만 시퀀스별 편차는 미확인.
14. **4Seasons 의 거의 전부.** §3.4 에서 1 순위로 올렸지만 이 저장소가 조사한 적 없는
    데이터셋이다. 미확인: 내부파라미터(fx), 정확한 배포 형식(undistorted 본이 정렬본과
    같은지), 총 용량, 시퀀스별 선택 다운로드 가능 여부, 접근 조건, `GNSSPoses.txt` 의
    정확한 열 구성과 좌표계, 그리고 **눈·비·야간 시퀀스가 각각 몇 개인지.**
    **다음 조사 대상 1 순위.**
15. **Oxford RobotCar SDK 의 `undistort()` 결과가 진짜 정렬 쌍인지.** SDK 는 demosaic +
    카메라별 왜곡보정 LUT 만 제공하고, "epipolar-rectified 쌍을 낸다" 는 서술은 문서
    어디에도 없다. XB3 는 동일 강체 바에 coplanar 배치라 보정 후 거의 정렬되겠지만,
    §1.6 의 요구를 만족하는지는 `extrinsics/` 로 `stereoRectify` 를 돌려 봐야 안다.
16. **RobotCar RTK 보류 traversal 의 정확한 수.** 웹사이트는 6 건, 논문 목록은 8 건으로
    불일치한다. **유일한 눈 traversal 이 보류 목록에 있다는 사실 자체는 확인되었다.**
17. **RobotCar 태그별 traversal 정확한 개수.** 인용한 sun ~45 / rain ~8 / night ~6–7 /
    snow 1 은 페이지 파싱 기반 개략치다.
18. **MS2(KAIST) 정답의 정확도 등급.** odometry 파일은 제공되나 RTK 급인지 미확인.
19. **Boreas 총 용량**, 그리고 라이선스 표기 불일치(논문·사이트 CC BY-NC 4.0 vs
    AWS Open Data Registry CC BY 4.0).
